# SocialHub — тест-кейсы в табличном формате

Социальная платформа для осознанного потребления контента с управляемой лентой и прозрачной модерацией.

## О документе

Ниже приведены тест-кейсы, оформленные в стиле модульных таблиц:
- **ID** — идентификатор теста;
- **Название теста** — короткое имя сценария;
- **Описание** — предусловие, что вводит пользователь, какой результат ожидается и как взаимодействуют микросервисы.

## Бизнес-правила, которые обязательно покрыты тестами

- **BR-1** — публикации разрешены только в сообществах;
- **BR-2** — не более 100 постов за 24 часа от одного пользователя в одном сообществе;
- **BR-3** — пользователь может состоять максимум в 30 сообществах одновременно.

## Условные тестовые данные

- Пользователь: **Иван Петров** (`ivan.petrov`, пароль `Passw0rd!`)
- Пользователь: **Мария Соколова** (`maria.sokolova`, пароль `Passw0rd!`)
- Администратор сообщества: **Анна Белова** (`anna.admin`, пароль `Passw0rd!`)
- Модератор платформы: **Павел Модераторов** (`pavel.mod`, пароль `Passw0rd!`)
- Сообщество: **architecture_club**
- Сообщество: **backend_daily**
- Сообщество для проверки лимита: **community_01 ... community_31**

## Модуль 1 — Auth & User Service (управление пользователями и профилем)

*Бизнес-логика регистрации, авторизации, профиля и статуса пользователя; сервис работает через API Gateway и хранит данные в PostgreSQL.*

| ID | Название теста | Описание |
|---|---|---|
| TC-01 | Регистрация — новый пользователь создан | **Предусловие:** логин `sergey.test` и email `sergey@test.local` ещё не существуют.<br>**Пользователь вводит:** логин `sergey.test`, email `sergey@test.local`, пароль `Passw0rd!`, имя `Сергей Тестов`.<br>**Ожидаемый результат:** на экране показывается успешная регистрация, создан личный кабинет, роль `Пользователь`.<br>**Проверка данных:** в БД появляются запись пользователя и профиль; пароль хранится в виде хеша.<br>**Сервисы:** Client → API Gateway → Auth & User Service → PostgreSQL. |
| TC-02 | Регистрация — дубликат логина | **Предусловие:** пользователь с логином `ivan.petrov` уже существует.<br>**Пользователь вводит:** логин `ivan.petrov`, email `ivan.new@test.local`, пароль `Passw0rd!`, имя `Иван Новый`.<br>**Ожидаемый результат:** форма показывает ошибку `Логин уже занят`; новый пользователь не создаётся.<br>**Проверка данных:** новых строк в таблицах пользователей и профилей нет.<br>**Сервисы:** Client → API Gateway → Auth & User Service → PostgreSQL. |
| TC-03 | Авторизация — корректный логин и пароль | **Предусловие:** учётная запись `ivan.petrov` активна и не заблокирована.<br>**Пользователь вводит:** логин `ivan.petrov`, пароль `Passw0rd!`.<br>**Ожидаемый результат:** пользователь входит в систему и попадает на главную страницу; создаётся сессия/токен.<br>**Проверка данных:** в журнале входов фиксируется успешная авторизация.<br>**Сервисы:** Client → API Gateway → Auth & User Service → PostgreSQL; API Gateway возвращает токен клиенту. |
| TC-04 | Авторизация — неверный пароль | **Предусловие:** логин `ivan.petrov` существует.<br>**Пользователь вводит:** логин `ivan.petrov`, пароль `WrongPass123`.<br>**Ожидаемый результат:** на экране сообщение `Неверный логин или пароль`; вход не выполняется.<br>**Проверка данных:** статус пользователя не меняется; создаётся запись об ошибочной попытке входа.<br>**Сервисы:** Client → API Gateway → Auth & User Service → PostgreSQL. |
| TC-05 | Профиль — изменение имени и описания | **Предусловие:** пользователь вошёл в систему.<br>**Пользователь вводит:** новое отображаемое имя `Иван Петров Архитектор`, описание `Люблю распределённые системы и C4 model`.<br>**Ожидаемый результат:** на странице профиля показываются обновлённые имя и описание.<br>**Проверка данных:** в БД профиля обновляются только изменённые поля; остальные поля профиля сохраняются без изменений.<br>**Сервисы:** Client → API Gateway → Auth & User Service → PostgreSQL. |
| TC-06 | Авторизация — заблокированный пользователь не может войти | **Предусловие:** модератор ранее установил пользователю статус `BLOCKED`.<br>**Пользователь вводит:** логин `maria.sokolova`, пароль `Passw0rd!`.<br>**Ожидаемый результат:** на экране сообщение `Аккаунт заблокирован`; вход запрещён.<br>**Проверка данных:** токен не выдаётся, профиль не открывается.<br>**Сервисы:** Client → API Gateway → Auth & User Service → PostgreSQL; статус проверяется до выдачи токена. |

*CRUD-операции над сообществами, вступление и выход, контроль лимита 30 подписок, разграничение ролей администратора сообщества и обычного участника.*

| TC-09 | Вступление в 31-е сообщество — отказ по BR-3 | **Предусловие:** пользователь уже состоит ровно в 30 сообществах.<br>**Пользователь вводит:** на странице `community_31` нажимает кнопку `Вступить`.<br>**Ожидаемый результат:** на экране ошибка `Достигнут лимит: не более 30 сообществ`; вступление не выполняется.<br>**Проверка данных:** новая запись о членстве не создаётся.<br>**Сервисы:** Client → API Gateway → Community Service → PostgreSQL; сервис синхронно проверяет количество подписок. |
| TC-10 | Выход из сообщества — участник удалён | **Предусловие:** пользователь уже состоит в `architecture_club` как обычный участник.<br>**Пользователь вводит:** нажимает кнопку `Покинуть сообщество` и подтверждает действие.<br>**Ожидаемый результат:** кнопка меняется на `Вступить`, посты сообщества больше не попадают в его ленту.<br>**Проверка данных:** запись о членстве удаляется или помечается неактивной.<br>**Сервисы:** Client → API Gateway → Community Service → PostgreSQL; далее Feed Service использует обновлённый список подписок. |

## Модуль 3 — Post Service (публикации и контент)

*Создание, редактирование и удаление постов внутри сообществ; хранение метаданных в PostgreSQL, контента в MongoDB; контроль BR-1 и BR-2.*

| ID | Название теста | Описание |
|---|---|---|
| TC-14 | Публикация поста в сообществе — успешное создание | **Предусловие:** Иван состоит в `architecture_club`; за последние 24 часа он опубликовал в этом сообществе 12 постов.<br>**Пользователь вводит:** в форме нового поста пишет заголовок `Паттерны интеграции`, текст `Рассмотрим Saga, Outbox и CQRS`, нажимает `Опубликовать`.<br>**Ожидаемый результат:** пост появляется на странице сообщества со статусом `Опубликован`.<br>**Проверка данных:** метаданные сохраняются в PostgreSQL, тело поста — в MongoDB, счётчик публикаций за сутки увеличивается до 13.<br>**Сервисы:** Client → API Gateway → Post Service → PostgreSQL + MongoDB; Post Service запрашивает Community Service для проверки членства. |
| TC-15 | Публикация на личной странице — запрещено по BR-1 | **Предусловие:** пользователь авторизован и находится в личном кабинете.<br>**Пользователь вводит:** нажимает `Создать пост` в своём профиле, пишет текст `Мой личный пост` и пытается сохранить.<br>**Ожидаемый результат:** система показывает сообщение `Публикации доступны только в сообществах`; пост не создаётся.<br>**Проверка данных:** ни в PostgreSQL, ни в MongoDB новых записей нет.<br>**Сервисы:** Client → API Gateway → Post Service; Post Service отклоняет запрос до записи в БД. |
| TC-16 | Публикация 100-го поста за сутки — разрешена по BR-2 | **Предусловие:** у пользователя уже есть 99 постов в `backend_daily` за последние 24 часа.<br>**Пользователь вводит:** заголовок `Пост №100`, текст `Это сотая публикация за сутки`, нажимает `Опубликовать`.<br>**Ожидаемый результат:** пост успешно публикуется, пользователь видит его в списке постов сообщества.<br>**Проверка данных:** лимит считается корректно; после сохранения количество постов становится 100.<br>**Сервисы:** Client → API Gateway → Post Service → PostgreSQL (синхронная проверка лимита) → MongoDB. |
| TC-17 | Публикация 101-го поста за сутки — отказ по BR-2 | **Предусловие:** у пользователя уже есть 100 постов в `backend_daily` за последние 24 часа.<br>**Пользователь вводит:** заголовок `Пост №101`, текст `Попытка превысить лимит`, нажимает `Опубликовать`.<br>**Ожидаемый результат:** на экране ошибка `Достигнут суточный лимит: 100 постов`; публикация не создаётся.<br>**Проверка данных:** счётчик не увеличивается, новых записей в БД нет.<br>**Сервисы:** Client → API Gateway → Post Service → PostgreSQL; сервис отклоняет публикацию до записи контента в MongoDB. |
| TC-18 | Редактирование собственного поста — изменяется только контент | **Предусловие:** Иван — автор поста `Паттерны интеграции` в `architecture_club`.<br>**Пользователь вводит:** меняет текст на `Рассмотрим Saga, Outbox, CQRS и Event Sourcing`, нажимает `Сохранить`.<br>**Ожидаемый результат:** на странице сообщества сразу отображается новая версия текста; автор и сообщество не меняются.<br>**Проверка данных:** в MongoDB обновляется тело поста, в PostgreSQL — дата последнего изменения.<br>**Сервисы:** Client → API Gateway → Post Service → PostgreSQL + MongoDB. |
| TC-19 | Удаление собственного поста — публикация скрыта из ленты | **Предусловие:** пользователь является автором поста и он уже виден в ленте подписчиков.<br>**Пользователь вводит:** на карточке поста нажимает `Удалить` и подтверждает действие.<br>**Ожидаемый результат:** пост исчезает со страницы сообщества и из ленты подписчиков.<br>**Проверка данных:** статус поста меняется на `DELETED` или запись удаляется согласно политике; действие фиксируется в аудите.<br>**Сервисы:** Client → API Gateway → Post Service → PostgreSQL + MongoDB; Post Service → Feed Service для инвалидирования кэша/обновления выдачи. |
| TC-20 | Публикация в чужом сообществе без участия — запрещена | **Предусловие:** пользователь не состоит в `backend_daily`.<br>**Пользователь вводит:** открывает прямую ссылку на форму публикации сообщества, пишет заголовок `Неавторизованный пост`, текст `Проверка доступа` и нажимает `Опубликовать`.<br>**Ожидаемый результат:** на экране ошибка `Вы не состоите в этом сообществе`.<br>**Проверка данных:** пост не создаётся; запись об отказе может попасть в аудит.<br>**Сервисы:** Client → API Gateway → Post Service → Community Service → PostgreSQL; при отрицательной проверке членства запись в БД постов не выполняется. |

## Модуль 4 — Feed Service (лента и ранжирование)

*Формирование ленты только из подписанных сообществ, ранжирование по популярности, использование Redis для горячих данных, деградация при отсутствии кэша.*

| ID | Название теста | Описание |
|---|---|---|
| TC-21 | Лента — показываются только подписанные сообщества | **Предусловие:** Иван подписан на `architecture_club` и `backend_daily`, но не состоит в `community_31`.<br>**Пользователь вводит:** открывает главную страницу и обновляет ленту.<br>**Ожидаемый результат:** в ленте отображаются посты только из `architecture_club` и `backend_daily`; публикаций из неподписанных сообществ нет.<br>**Проверка данных:** Feed Service использует список подписок пользователя, полученный через Community Service или предварительно кэшированный.<br>**Сервисы:** Client → API Gateway → Feed Service → Redis; при необходимости Feed Service → Community Service/Post Service → PostgreSQL. |
| TC-22 | Лента — более популярный пост выше менее популярного | **Предусловие:** в двух подписанных сообществах есть пост A с 250 лайками и пост B с 30 лайками.<br>**Пользователь вводит:** открывает ленту и сравнивает порядок карточек.<br>**Ожидаемый результат:** пост A расположен выше поста B; порядок соответствует алгоритму ранжирования по популярности.<br>**Проверка данных:** Feed Service использует актуальные метрики популярности из Post Service/кэша.<br>**Сервисы:** Client → API Gateway → Feed Service → Redis; при промахе кэша Feed Service → Post Service → PostgreSQL. |
| TC-23 | Лента — у пользователя без подписок пустой результат | **Предусловие:** новый пользователь не вступил ни в одно сообщество.<br>**Пользователь вводит:** открывает главную страницу после входа.<br>**Ожидаемый результат:** отображается пустое состояние `Подпишитесь на сообщества, чтобы увидеть ленту`.<br>**Проверка данных:** ошибок сервера нет, пустой результат считается корректным ответом.<br>**Сервисы:** Client → API Gateway → Feed Service → Community Service/PostgreSQL; Feed Service возвращает пустой набор. |
| TC-24 | Лента — кэш недоступен, данные возвращаются из БД | **Предусловие:** Redis временно недоступен, в подписанных сообществах есть посты.<br>**Пользователь вводит:** обновляет ленту страницы.<br>**Ожидаемый результат:** лента открывается корректно, возможно медленнее, но без ошибки для пользователя.<br>**Проверка данных:** Feed Service переключается на чтение из базовых хранилищ и фиксирует деградацию в логах.<br>**Сервисы:** Client → API Gateway → Feed Service → Redis (ошибка) → Post Service/Community Service → PostgreSQL. |
| TC-25 | Лента — соблюдение NFR по времени загрузки | **Предусловие:** средняя нагрузка, пользователь подписан на 10 сообществ, в каждом есть не менее 200 постов.<br>**Пользователь вводит:** открывает страницу ленты с обычного клиента.<br>**Ожидаемый результат:** первый экран ленты отображается не более чем за 5 секунд.<br>**Проверка данных:** измеряется общее время ответа; при превышении тест не проходит.<br>**Сервисы:** Client → API Gateway → Feed Service → Redis/PostgreSQL. |

|---|---|---|

## Модуль 6 — Moderation Service (жалобы, блокировки, аудит)

|---|---|---|
| TC-31 | Жалоба на пост — пользователь отправляет обращение | **Предусловие:** в ленте есть пост, который пользователь считает нарушающим правила.<br>**Пользователь вводит:** на карточке поста нажимает `Пожаловаться`, выбирает причину `Спам`, комментарий `Массовая реклама без смысла`, подтверждает отправку.<br>**Ожидаемый результат:** система показывает сообщение `Жалоба отправлена`; пользователь видит, что обращение зарегистрировано.<br>**Проверка данных:** в БД модерации создаётся запись жалобы со статусом `NEW`.<br>**Сервисы:** Client → API Gateway → Moderation Service → PostgreSQL. |
| TC-32 | Модератор удаляет нарушающий пост | **Предусловие:** Павел вошёл как модератор платформы; на пост уже есть жалоба.<br>**Пользователь вводит:** в панели модерации открывает жалобу и нажимает `Удалить пост`.<br>**Ожидаемый результат:** пост исчезает из сообщества и ленты; статус жалобы меняется на `RESOLVED`.<br>**Проверка данных:** действие сохраняется в аудит, автор поста получает уведомление.<br>**Сервисы:** Client → API Gateway → Moderation Service → PostgreSQL; Moderation Service → Post Service → PostgreSQL + MongoDB; Moderation Service → Notification Service. |
| TC-33 | Модератор блокирует пользователя | **Предусловие:** пользователь многократно нарушал правила платформы.<br>**Пользователь вводит:** в карточке пользователя нажимает `Заблокировать`, выбирает срок `7 дней`, причина `Повторный спам`.<br>**Ожидаемый результат:** статус пользователя меняется на `BLOCKED`, вход в систему становится невозможен до разблокировки или истечения срока.<br>**Проверка данных:** в БД создаются записи блокировки и аудита; пользователю отправляется уведомление.<br>**Сервисы:** Client → API Gateway → Moderation Service → PostgreSQL; Moderation Service → Auth & User Service → PostgreSQL; Moderation Service → Notification Service. |
| TC-34 | Модератор не может читать личные сообщения | **Предусловие:** модератор авторизован, но не имеет специальных полномочий на доступ к ЛС.<br>**Пользователь вводит:** пытается открыть диалог Ивана и Марии через модераторскую панель или прямую ссылку.<br>**Ожидаемый результат:** интерфейс показывает `Доступ к личным сообщениям запрещён`; переписка не раскрывается.<br>**Проверка данных:** Messaging Service не возвращает содержимое сообщений; событие отказа можно записать в аудит.<br>**Сервисы:** Client → API Gateway → Messaging Service/Auth & User Service → отказ; доступ блокируется политикой безопасности. |
| TC-35 | Локальная модерация — администратор сообщества удаляет пост участника | **Предусловие:** Анна — администратор `architecture_club`, Мария — участник сообщества и автор спорного поста.<br>**Пользователь вводит:** на странице сообщества открывает меню поста Марии и нажимает `Удалить пост`.<br>**Ожидаемый результат:** пост удаляется только в рамках сообщества; действие фиксируется как локальная модерация, а не глобальная блокировка.<br>**Проверка данных:** запись аудита содержит ID сообщества и роль инициатора `COMMUNITY_ADMIN`.<br>**Сервисы:** Client → API Gateway → Community Service → Post Service → PostgreSQL + MongoDB; Community Service → Moderation Service/PostgreSQL для аудита. |
| TC-36 | Аудит — любое действие модератора фиксируется в журнале | **Предусловие:** ранее были выполнены удаление поста, обработка жалобы или блокировка пользователя.<br>**Пользователь вводит:** модератор открывает раздел `Журнал действий` и фильтрует по своему имени и дате.<br>**Ожидаемый результат:** система показывает список действий с временем, объектом воздействия и причиной решения.<br>**Проверка данных:** записи аудита присутствуют и доступны для поиска по фильтрам.<br>**Сервисы:** Client → API Gateway → Moderation Service → PostgreSQL. |

## Модуль 7 — Notification Service и Email Provider (уведомления)

*Асинхронная доставка событий пользователям; Notification Service получает события от внутренних сервисов и отправляет email через внешний SMTP-провайдер.*

|---|---|---|
| TC-37 | Уведомление — автор получает письмо о публикации предложенного поста | **Предусловие:** Мария отправила предложенный пост, а Анна его одобрила.<br>**Пользователь вводит:** Мария ничего дополнительно не вводит; действие инициируется внутри системы после модерации предложения.<br>**Ожидаемый результат:** на email `maria@test.local` приходит письмо с темой `Ваш пост опубликован в architecture_club`.<br>**Проверка данных:** событие об одобрении передаётся в Notification Service и успешно доставляется через SMTP.<br>**Сервисы:** Community Service/Post Service → Notification Service → MongoDB (очередь/транспорт) → Email Provider. |
| TC-38 | Уведомление — пользователь получает письмо о блокировке | **Предусловие:** модератор заблокировал пользователя на 7 дней.<br>**Пользователь вводит:** действие выполняет модератор; заблокированный пользователь затем открывает почту.<br>**Ожидаемый результат:** приходит письмо с причиной блокировки и сроком ограничения.<br>**Проверка данных:** событие создаётся Moderation Service и проходит весь путь до внешнего SMTP-провайдера.<br>**Сервисы:** Moderation Service → Notification Service → MongoDB → Email Provider. |
| TC-39 | SMTP недоступен — бизнес-действие не откатывается | **Предусловие:** внешний Email Provider временно не отвечает.<br>**Пользователь вводит:** Анна публикует предложенный пост или модератор блокирует пользователя, что должно вызвать уведомление.<br>**Ожидаемый результат:** основное действие системы выполняется успешно; письмо может не уйти сразу, но ошибка не ломает публикацию или блокировку.<br>**Проверка данных:** Notification Service фиксирует неудачную попытку доставки и может оставить событие на повторную отправку.<br>**Сервисы:** Community Service/Moderation Service → Notification Service → Email Provider (ошибка); бизнес-сервис завершает свою операцию независимо. |
| TC-40 | Асинхронный транспорт — уведомление создаётся без задержки для пользователя | **Предусловие:** в системе включены email-уведомления; Notification Service использует MongoDB как транспорт событий.<br>**Пользователь вводит:** отправляет действие, которое порождает уведомление, например жалобу или предложенный пост.<br>**Ожидаемый результат:** пользователь сразу видит успешное выполнение основного действия, не ожидая фактической отправки email.<br>**Проверка данных:** в MongoDB Notification Service появляется запись события со статусом `NEW` или `PENDING`, далее событие обрабатывается асинхронно.<br>**Сервисы:** Client → API Gateway → бизнес-сервис → Notification Service → MongoDB → Email Provider. |
